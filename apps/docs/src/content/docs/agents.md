`pane mcp` поднимает MCP-сервер поверх stdio и отдаёт операции Pane как
инструменты. Агент — Claude Code, Cursor, свой скрипт на SDK — получает
возможность посмотреть, что реально ушло в сеть, поднять мок, прогнать сценарий
и проверить результат, не трогая ни GUI, ни исходники приложения.

То же самое доступно и просто из терминала — см. [CLI `pane`](/docs/cli/).
MCP отличается тем, что инструменты описаны схемой, и агент не занимается
разбором текстового вывода.

## Подключение

Сервер — это одна команда, `pane mcp`, без флагов. Любой MCP-клиент настраивается
одинаково:

```json
{
  "mcpServers": {
    "pane": {
      "command": "pane",
      "args": ["mcp"]
    }
  }
}
```

Claude Code — то же самое одной строкой:

```sh
claude mcp add pane -- pane mcp
```

Нужна другая директория данных (например, черновая для CI) —
`"args": ["mcp", "--data-dir", "/tmp/scratch-pane"]` или переменная
`PANE_DATA_DIR` в окружении клиента.

Сервер работает и при открытом приложении (тогда он цепляется к нему и правки
видны в окне сразу), и без него — см. [Pane без окна](/docs/headless/).

## Инструменты

| Инструмент | Что делает |
| --- | --- |
| `pane_doctor` | состояние прокси, устройства, adb, отпечаток CA. С него начинают |
| `pane_proxy_status` | запущен ли прокси, на каком адресе, сколько captures |
| `pane_captures_list` | последние captures с `state` и `matched_rule_name`, с фильтром |
| `pane_captures_count` | число captures под фильтр — самая дешёвая проверка |
| `pane_capture_get` | один capture с заголовками запроса и ответа |
| `pane_capture_body` | тело запроса или ответа, обрезано до `max_bytes` (8192 по умолчанию) |
| `pane_captures_wait` | заблокироваться, пока не наберётся `count` под фильтр, либо `timeout_sec` |
| `pane_captures_clear` | стереть все captures — между сценариями |
| `pane_rules_list` | правила с их состоянием, матчерами и статусом ответа |
| `pane_rule_mock` | создать stub-правило |
| `pane_rule_set_enabled` | включить/выключить правило по подстроке имени или id |
| `pane_rules_set_enabled_bulk` | пачкой: вся библиотека, одна коллекция или всё вне коллекций |
| `pane_collections_list` | коллекции и сколько в каждой правил |
| `pane_collection_set_enabled` | включить/выключить все правила коллекции |
| `pane_collection_only` | переключиться ровно на один сценарий |
| `pane_collection_delete` | удалить коллекцию (правила переезжают в Ungrouped) |
| `pane_devices_list` | спаренные устройства и стоит ли на них CA |
| `pane_devices_attached` | что воткнуто по USB прямо сейчас |
| `pane_device_add` | спарить устройство; нужен запущенный прокси |
| `pane_logcat_query` | строки логов Android с фильтром `tag: msg: level: pid: app:` |

Инструменты собраны под задачу, а не отзеркалены один-в-один с командами CLI.
Главное отличие — `pane_captures_wait`: в MCP нет стриминга, поэтому
`captures tail` превращается в блокирующий вызов, который возвращает то, что
увидел за отведённое время.

## Гигиена контекста

Тела ответов и списки captures съедают контекст быстрее всего остального, поэтому
идти надо сверху вниз, а не сразу за телом:

1. `pane_captures_count` с фильтром — один число, дальше уже понятно, есть ли о чём говорить;
2. `pane_captures_list` с узким фильтром и небольшим `limit`;
3. `pane_capture_get` по конкретному id;
4. `pane_capture_body` — и только с `max_bytes`.

Из терминала для больших тел есть `pane captures body <id> --res --out FILE`:
файл пишется целиком и в контекст не попадает вовсе.

## Докажи, что ответ пришёл из мока

Фильтр `state:stubbed` говорит, что ответ отдал *какой-то* мок. На большой
библиотеке правил это гораздо слабее, чем знать, **какой именно**: прогон,
сматчивший не то правило, выглядит так же зелено. Проверять надо обе стороны:

```sh
pane captures count --filter 'state:stubbed rule:orders-500'          # должно быть ≥ 1
pane captures count --filter 'host:api.example.com state:completed'   # должно быть 0
```

Первое — «моё правило ответило». Второе — «до живого бэкенда ничего не дошло».
Только вместе они означают то, что нужно.

Если сценарии разведены по устройствам, `device:` нужен на обеих сторонах —
иначе за этот телефон ответит трафик соседнего:

```sh
pane captures count --filter 'device:pixel state:stubbed rule:checkout-ok'  # ≥ 1
pane captures count --filter 'device:pixel rule:orders-500'                 # 0
```

Отсюда же следует, почему сценарии переключаются целиком:

```sh
pane rules disable --all
pane rules enable --collection orders-error
# или короче:
pane collections only orders-error
```

Оставленная включённой предыдущая коллекция — классический способ получить
зелёный прогон, который ничего не доказывает: два правила на один host и path,
отвечает то, что выше по приоритету, а `state:stubbed` всё равно совпадает.

:::tip
Если сценарий смешивает stub- и patch-правила, проверяй `state:stubbed,patched` —
на ответе, который сделало patch-правило, проверка только на `stubbed` провалится.
А `state:tunneled` означает, что клиент не доверился нашему CA и соединение
прошло насквозь незашифрованным: это проблема доверия сертификату, а не матчинга
правил.
:::

## Скриптовый прогон

`pane captures tail` отдаёт NDJSON, первая строка всегда `ready` — её нужно
дождаться и только потом дёргать приложение. Иначе гонка на первом запросе,
которую затыкают `sleep`'ом, а флакающие прогоны берутся именно оттуда.

```bash
#!/usr/bin/env bash
set -euo pipefail
export PANE_FORMAT=json

pane collections only orders-error
pane captures clear --yes

exec 3< <(pane captures tail --filter 'host:api.example.com' --count 1 --timeout 45)
read -r -u 3 _ready                      # блокируется до {"event":"ready",…}

maestro test flows/orders_error.yaml     # вот теперь дёргаем приложение

read -r -u 3 hit || true
printf '%s' "$hit" | jq -r 'select(.event=="capture") | "\(.status) \(.matched_rule_name)"'

test "$(pane captures count --filter 'state:stubbed rule:orders-500')" -ge 1
test "$(pane captures count --filter 'host:api.example.com state:completed')" -eq 0
```

Вердикт несёт код возврата: **7 означает, что `--count` не набрался до
`--timeout`** — то есть проверка провалилась, а не инструмент сломался.
Последняя строка потока — всегда `{"event":"end","reason":"count"|"timeout"|"signal"}`.

## Скиллы в репозитории

В `.claude/skills/` лежат три готовых скилла — их можно скопировать к себе в
проект или использовать как образец инструкции для любого агента:

| Скилл | О чём |
| --- | --- |
| `pane-debug` | смотреть живой трафик: лестница детализации, tail, корреляция с logcat |
| `pane-mock` | моки и проверки: коллекции, `only`, доказательство «ответил мок» |
| `pane-run` | запуск и остановка инстанса, разбор конфликта за директорию |

Рядом, в корне репозитория, лежит `AGENTS.md` — сжатая шпаргалка на одну
страницу для агента, который зашёл в проект впервые.

При расхождении любой документации с реальностью источник истины один:

```sh
pane schema      # дерево команд, обе грамматики фильтров и exit-коды, как JSON
```
