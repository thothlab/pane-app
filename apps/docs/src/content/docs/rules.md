Pane поддерживает два режима подмены ответов на запросы, проходящие через прокси:

- **Stub** — апстрим не вызывается, отдаётся целиком заранее подготовленный ответ.
- **Patch** — реальный запрос идёт на сервер, его ответ перехватывается и поверх него применяется список патчей.

Patch удобен в сценариях, где клиент зависит от server-generated полей (token, timestamps, ids) — они остаются настоящими, а ты подменяешь только нужные значения для теста.

## Быстрый способ: из Captures

В **Captures** правый клик по строке открывает меню «Добавить в Rules». В нём перечислены существующие коллекции, пункт «Без коллекции» и «Новая коллекция…» (создаётся с дефолтным именем `Из захваченных` — переименовать можно позже).

После выбора Pane создаёт stub-правило, заполненное из захваченного запроса:

- `method`, `host_glob`, `path_glob` (query из пути отрезается — `match_params` остаётся пустым, чтобы мок матчился независимо от query),
- **Request body (JSON)** — если у запроса было JSON-тело, оно префиллится сюда целиком (pretty-printed), см. раздел ниже,
- `res_status`, `res_headers`, `res_body` берутся как есть из ответа.

Сразу после добавления Pane переключает Rules-вкладку в режим редактирования этого правила — можно прямо там подкорректировать имя, тело, заголовки и нажать Save.

## Матчинг по телу запроса (JSON-subset)

Поле **Request body (JSON)** в секции Match задаёт JSON, который движок проверяет на **вхождение** в тело запроса (deep subset). Это даёт матчинг по **вложенным** полям — в отличие от `match_params`, которые видят только скаляры верхнего уровня query/тела.

Семантика `template ⊆ actual`:

- **объекты** — каждый ключ шаблона должен найтись в теле и совпасть рекурсивно; лишние поля в запросе допускаются;
- **массивы** — позиционным префиксом: тело не короче шаблона, и `template[i]` входит в `actual[i]`;
- **скаляры** — точное равенство;
- `{}` — матчит любой JSON-объект; пустое поле / NULL — тело не матчим;
- тело не JSON или не содержит шаблон — правило **не** срабатывает (fail-closed).

```jsonc
// Request body (JSON):
{ "hidePaid": true, "period": { "from": "2026-01" } }
// сматчит любой запрос, где есть hidePaid:true И period.from:"2026-01",
// что бы ещё ни лежало в теле
```

> ⚠️ **Volatile-поля.** Захваченное тело содержит уникальные на запрос значения (`requestId` — UUID и т.п.). Матч точный, поэтому оставленный `requestId` сделает правило молча неработающим на следующих запросах. Редактор подсвечивает UUID в теле предупреждением — **удали** такие поля из JSON. (Числа: `0` и `0.0` сравниваются как разные — в норме не мешает, т.к. клиент сериализует одинаково.)

## Редактор тела ответа

Тело ответа редактируется в JSON-aware textarea — ключи, строки, числа, `true`/`false`/`null` подсвечены цветами под темой Pane. Подсветка делается на лету через прозрачный textarea поверх `<pre>` с регулярка-токенайзером, без внешних редакторных библиотек.

Рядом с заголовком поля есть две кнопки:

- **Format** (`{ }`) — `JSON.parse → JSON.stringify(..., null, 2)`, отступы 2 пробела. Если содержимое не валидный JSON, на 2.5 секунды появится inline-сообщение «Invalid JSON: …» — ничего не подменяется. Пустое тело даст «Body is empty». Format засчитывается как правка, кнопка Save станет красной.
- **Expand / Collapse** — переключает высоту textarea между «компактной» (12 rem ≈ 12 строк) и развёрнутой (70vh с минимумом 400 px). Состояние сохраняется в `localStorage` — открыл крупный JSON один раз, дальше каждый редактор открывается уже в развёрнутом виде.

## Индикатор несохранённых правок

Кнопка **Save** становится красной как только пользователь правит любое поле редактора (имя, host glob, method, статус, заголовки, тело, патчи, …). После успешного сохранения — снова синяя. На ошибке сохранения остаётся красной, чтобы было видно, что несохранённое не ушло. Это локально для текущего экземпляра редактора: восстановление черновика из localStorage не подсветит Save красным (правка не из текущей сессии).

## Чекбокс-тогглеры

В списке правил у каждого правила слева — небольшой чекбокс (включено/выключено вместо прежнего pill-свитча). У заголовка коллекции — такой же чекбокс рядом с шевроном:

- все правила в коллекции включены → галочка, клик отключает всё;
- все выключены → пустой квадрат, клик включает всё;
- смешанное состояние → минус (`−`) внутри квадрата, клик включает всё.

Один клик меняет статус только тех правил, которые отличаются от целевого состояния, остальные не трогаются.

## Состояние редактора сохраняется

Состояние Rules-вкладки переживает переключение вкладок и перезапуск приложения:

- какие коллекции свёрнуты,
- какое правило сейчас редактируется,
- черновик всех полей редактора, **включая** текст тела ответа в textarea.

Это покрывает типичный флоу «открыл правило → ушёл в Captures скопировать что-то → вернулся → вставил → сохранил» — раньше после возврата редактор был закрыт и приходилось разворачивать заново. Черновик стирается только при Save, Cancel или нажатии «свернуть без сохранения» (≡ стрелка ↑ в шапке редактора).

## Шеринг правил: импорт и экспорт

Собранный набор моков хочется сохранять — и передавать коллеге. Правила выгружаются и подгружаются из `.json` на трёх уровнях.

**Экспорт**:

- **Одно правило** — иконка Download в строке правила (между Edit и Delete). Сохраняет `<имя>.pane-rule.json` с правилом и инлайн-телом ответа.
- **Коллекция целиком** — иконка Download в заголовке коллекции. Сохраняет `<имя>.pane-collection.json` со всеми её правилами.
- **Всё сразу** — кнопка *Export all* в шапке вкладки. Сохраняет `pane-rules.json` со всеми коллекциями (включая Ungrouped) и всеми правилами.

Тела правил кладутся в файл в base64 — он самодостаточен, никаких отдельных бинарников рядом носить не нужно.

**Импорт**:

Кнопка *Import* в шапке открывает файл-пикер. Поле `kind` внутри файла решает, что создать: одно правило, коллекцию с правилами или всю библиотеку. Действие аддитивное — текущие правила и коллекции не трогаются.

**Конфликты имён**: каждой импортированной сущности выдаётся новый UUID. Если коллекция или правило с таким же именем уже есть — импорт ложится рядом дубликатом (переименовать или удалить — на твоё усмотрение). Никаких prompt'ов «skip/overwrite» нет, два одинаковых имени — это сознательно ОК.

**Формат**: `{ format: "pane-rules", version: 1, kind, exported_at, collections, rules }`. Ручное редактирование JSON допускается, но без подсказок — невалидные поля всплывут как ошибка бэкенда при импорте.

## Где это настраивается

Sidebar → **Rules** → коллекция → правило в режиме `Patch — forward, then mutate`.

Правило матчится по тем же признакам, что и в Stub-режиме: host glob, method, path glob, query/body параметры. Если правило срабатывает — после получения ответа от сервера движок применяет список патчей.

## Синтаксис path

Путь — это dot-notation, который ходит по «виртуальному дереву ответа»:

| Префикс | Что меняет |
|---|---|
| `status` | HTTP-статус ответа |
| `headers.<Name>` | Заголовок ответа (case-insensitive) |
| `body.<dot.path>` | Поле в JSON-теле |
| `<dot.path>` | Тоже body — префикс `body.` опционален, так что `user.fio` ≡ `body.user.fio` |

Внутри body-пути:

- `a.b.c` — вложенный объект.
- `a.b[0]` — элемент массива по индексу.
- `a.b[-]` — добавить в конец массива (только в op `set` / `append`).

## Виды операций

| op | Что делает |
|---|---|
| `set` | Установить значение в path. Если родительских объектов нет — создаст. |
| `delete` | Удалить поле объекта или элемент массива по index. |
| `append` | Добавить элемент в массив (path указывает на массив). |

## Значение (value)

Парсится как JSON, с fallback на строку:

- `qwerty` → строка `"qwerty"`
- `777` → число
- `true` / `false` / `null` → bool / null
- `{"a":1}` → объект
- `["x","y"]` → массив

Если нужно подменить поле строкой, похожей на число (`"123"`), пиши `"123"` с кавычками.

## Пример 1. Подмена одного поля

Сервер отвечает:

```json
{
  "user": { "uid": 2715, "fio": "ТГ ГИС МТ", ... },
  "token": { "id": "ed821640d251...", ... }
}
```

Хочу: имя `fio` подменить на тестовое, оставить настоящий `token`.

**Mode**: Patch
**Match**: POST `/api/auth`
**Patches**:

```
op    | path           | value
------+----------------+------------
set   | user.fio       | "Тестовый"
```

Реальный токен останется живым, следующие запросы пройдут авторизацию.

## Пример 2. Заменить массив объектов

Сервер отвечает списком ~130 объектов:

```json
{ "objects": [ {...}, {...}, ... 130 элементов ], "_links": {...} }
```

Хочу: оставить в массиве **только один** объект (для теста UI пагинации, выпадайки, и т.п.).

### Вариант A — одно правило (рекомендуется)

Заменить весь массив сразу. В value — JSON-массив с одним элементом.

```
op    | path           | value
------+----------------+----------------------------------------------------------
set   | body.objects   | [{"uid":6,"id":6,"name":"ЗТК объект","priority":2}]
```

Обрати внимание: путь **`body.objects`** (без `[0]`!) и value начинается с `[` — это JSON-массив, не объект.

### Вариант B — два патча по очереди

Если удобнее в логике «очистить + добавить»:

```
op       | path           | value
---------+----------------+-------------------------
set      | body.objects   | []
append   | body.objects   | {"uid":6,"id":6,"name":"ЗТК объект","priority":2}
```

`set ... = []` очищает массив, `append` добавляет один элемент. Патчи применяются по порядку.

### Чего НЕ делать (типичная ошибка)

```
op    | path              | value
------+-------------------+----------------
set   | body.objects[0]   | {...}             ← заменит только нулевой элемент
```

При такой записи массив длиной 130 не меняется — просто первый элемент перезаписывается, остальные 129 остаются. UI всё ещё видит длинный список.

Правило: **`[0]` — это индекс конкретного элемента, а сам `body.objects` (без индекса) — весь массив.**

## Задержка (delay)

В обоих режимах есть поле **`delay (ms)`** в Response-секции. В Stub-режиме задержка применяется перед отправкой ответа. В Patch-режиме — после получения реального ответа от сервера, перед записью клиенту. Удобно симулировать медленный сервер.

---

## Что попадёт в Captures

- Stub-режим → `state='stubbed'`.
- Patch-режим → `state='patched'`. В вкладке Response видно уже подменённое тело — так клиент его и получил.

## Когда патч молча не сработает

- Body не является валидным JSON → body-патчи пропускаются (warning в лог), status/headers-патчи всё равно применяются.
- Content-Type ответа не json-подобный → body не парсится, body-патчи пропускаются.
- Путь указывает на несуществующий индекс массива в `delete` / `append` (для `append` индексов вообще не должно быть).
- Невалидный JSON в value → трактуется как строка, что иногда даёт неожиданное `"true"` вместо `true`.

Если правило не работает как ожидалось — посмотри, что реально лежит в captures для этого запроса, и сверь путь.
