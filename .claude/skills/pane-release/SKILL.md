# Релиз Pane

Внутренний скилл сопровождающего. Вызов скилла - явная просьба о push: на этом
пути `git push` разрешён, но только после одного подтверждения пользователя
(шаг 5). Остальные правила коммитов - из глобального `CLAUDE.md`: русский язык,
`-` и `->`, без длинного тире и типографских кавычек.

Публичное описание процесса - `apps/docs/src/content/docs/reference/releases.md`.
Там написано про релиз-ветку и PR; на деле релизы идут прямо в `main` (так
вышли 0.3.4-0.3.7). Скилл следует практике.

## 1. Состояние

```bash
git fetch -q && git status -sb | head -1     # ветка main, без "behind"
git status --short                            # чисто
git describe --tags --abbrev=0                # прошлый тег
git log --oneline "$(git describe --tags --abbrev=0)"..HEAD
```

- Не `main` или есть незакоммиченное - остановиться и спросить. Чужие
  незакоммиченные правки в релиз не тащить.
- `ahead N` - эти коммиты уйдут вместе с релизом. Перечислить их пользователю
  на шаге 5, включая docs-коммиты, которые просто не успели запушить.
- Коммитов с прошлого тега нет - релизить нечего, сказать и остановиться.

## 2. Номер версии

Версия - `version` в `Cargo.toml` (workspace). По умолчанию patch: в 0.x новые
фичи тоже выходили patch-версиями (0.3.5 добавил query-параметры). Minor -
только если пользователь попросил или коммиты ломают совместимость (CLI,
формат правил, IPC). Названную пользователем версию брать как есть.

## 3. Поднять версию

Ровно эти файлы, все три должны совпасть:

```bash
OLD=0.3.7 NEW=0.3.8
sed -i '' "s/^version = \"$OLD\"/version = \"$NEW\"/" Cargo.toml
sed -i '' "s/\"version\": \"$OLD\"/\"version\": \"$NEW\"/" package.json src-tauri/tauri.conf.json
cargo update -q -w --offline                  # Cargo.lock: версии крейтов workspace
grep -n "\"version\": \"$NEW\"\|^version = \"$NEW\"" Cargo.toml package.json src-tauri/tauri.conf.json
```

`grep` должен найти три строки. `git diff --stat` после шага 4 - те же пять
файлов, что в прошлом релизе: `CHANGELOG.md`, `Cargo.lock`, `Cargo.toml`,
`package.json`, `src-tauri/tauri.conf.json`.

## 4. CHANGELOG

Новая секция над прошлой, дата - сегодня:

```markdown
## [0.3.8] — 2026-10-21

### Добавлено

- **Короткий заголовок пользовательским языком.** Абзац: что видит
  пользователь, где это включается или выключается, что не затронуто.
```

- Длинное тире в заголовке секции оставить: так оформлены все прошлые
  секции, и по `## [X.Y.Z] — ` их режет шаг 7.
- Разделы - из Keep a Changelog: `Добавлено`, `Изменено`, `Исправлено`.
  Пустые не писать.
- Источник - `feat`/`fix` коммиты с прошлого тега. `docs`, `chore`, `test`,
  `refactor` без видимого эффекта не попадают.
- Текст пишется для пользователя приложения, а не пересказывает коммит.
  Имена классов и файлов - только если без них непонятно.

## 5. Проверки и подтверждение

```bash
cargo check -q --workspace && pnpm -s typecheck && pnpm -s test
```

Упало - чинить или остановиться, тег на красное не ставить.

Затем один `AskUserQuestion`: «Выпускаем X.Y.Z?» с опциями «Да» / «Нет». В
тексте вопроса - версия, список коммитов, которые уйдут (из шага 1), и
секция CHANGELOG. «Нет» - оставить изменения незакоммиченными и спросить, что
поправить.

## 6. Коммит, push, тег

```bash
git add CHANGELOG.md Cargo.lock Cargo.toml package.json src-tauri/tauri.conf.json
git commit -q -m "chore(release): $NEW" -m "Co-Authored-By: <атрибуция из system-reminder>"
git push origin main
git tag -a "v$NEW" -m "v$NEW"
git push origin "v$NEW"
```

Тег - только после того, как `main` ушёл: release.yml собирает коммит, на
который указывает тег, и этот коммит должен быть на удалённом `main`.

## 7. Дождаться CI

```bash
gh run list --limit 3 --json databaseId,workflowName,headBranch,status
```

Найти run `release` с `headBranch == vX.Y.Z` и ждать его в фоне
(`run_in_background`), а не опросом:

```bash
gh run watch <id> --exit-status --interval 60 >/dev/null 2>&1; echo "exit=$?"
gh run view <id> --json conclusion,jobs --jq '.conclusion, (.jobs[] | "\(.name): \(.conclusion)")'
```

Сборка идёт около 15 минут (0.3.7 - 15 минут). Пока ждём, сообщить пользователю run id и что
будет дальше.

Упала хотя бы одна сборка - `publish` не запускается, релиз остаётся
черновиком, пользователи его не видят. Показать лог упавшего job
(`gh run view <id> --log-failed | tail -60`) и не трогать тело релиза.

## 8. Тело релиза

Только после завершения всего workflow: каждая платформенная сборка
перезаписывает тело шаблоном, ранняя правка затрётся.

Тело = секция версии из CHANGELOG + блок `**Установка:**` из прошлого релиза.
Шаблон workflow англоязычный, блок установки в прошлых релизах - русский,
поэтому берём его оттуда.

```bash
d=$(mktemp -d)
{ awk -v v="$NEW" 'index($0, "## [" v "]")==1 {f=1; next} /^## \[/ {f=0} f && !(n==0 && /^$/) {n=1; print}' CHANGELOG.md
  echo
  gh release view "v$OLD" --json body --jq .body | awk '/^\*\*Установка:\*\*/ {f=1} f'
} > "$d/notes.md"
cat "$d/notes.md"            # проверить глазами: есть и секция, и «Установка»
gh release edit "v$NEW" --notes-file "$d/notes.md"
```

Здесь только `awk`: `sed` на macOS - BSD, однострочники вида `1{/^$/d}` в нём
падают, и при `;` в цепочке команд в тело уходит только блок установки.

Проверка результата:

```bash
gh release view "v$NEW" --json isDraft,url,assets --jq '"draft=\(.isDraft) \(.url)", (.assets[].name)'
```

`draft=false`, есть `latest.json`, три платформы по таблице артефактов из
`releases.md`.

## 9. Хвосты

- `Правки.md` в vault (`Projects/Pane/Правки.md`, процедура - скилл
  `vault-reporting`): у записей, чьи коммиты вошли в релиз, дописать в строку
  **Коммит:** «Вышло в релизе X.Y.Z», закоммитить и запушить vault.
- Итог пользователю: ссылка на релиз, статус каждой платформы, список
  артефактов, что было отправлено вместе с релизом сверх него (шаг 1).
